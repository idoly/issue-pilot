# Code Design & Review

目标：**正确、复用、职责清晰、变化局部化、整体简洁**。按任务风险应用规则，不增加无收益流程。适用于代码、配置、依赖和构建；仅在授权范围内修改。Node.js 专项同时覆盖 JavaScript、TypeScript、服务、CLI 和库，不预设框架。

**规则力度**：授权边界、明确契约和证据纪律必须遵守；专项规则仅在涉及对应机制时应用；模式替换、Worker、缓存和依赖引入等优化须有具体收益。不要求每项任务遍历全部规则或运行完整工具链。

## 一、设计原则

1. **正确性优先**：守住业务行为、安全、数据一致性、契约与必要兼容性。
2. **业务知识集中**：同一规则明确归属、统一维护；仅代码相似但语义不同的不强行合并。
3. **变化局部化**：围绕真实变化点组织职责与依赖（依据可来自修改历史、已确认扩展、依赖方向、领域归属或契约稳定性），不为假设需求预建扩展点。
4. **恰当抽象**：抽象须减少重复维护、耦合或修改扩散，收益应超过理解、测试与维护成本。
5. **整体简洁**：优先复用项目惯例、现有实现、标准库与框架能力；不以代码量或文件数衡量设计质量。
6. **证据驱动**：性能先测量，清理先核实引用；不把推测当事实。

## 二、设计决策

先确认**语义、正确性、契约和授权**，再比较直接实现、复用现有能力和新增抽象：

| 决策 | 何时考虑 | 何时避免 |
|---|---|---|
| 合并重复 | 同一业务规则需要同步维护，语义一致 | 仅代码形状相似，失败或业务语义不同，或规则归属不同 |
| 新增接口/策略 | 真实多实现、外部可替换边界或明确的修改扩散 | 单实现、无真实变化需求、增加无收益层级 |
| 拆分类/模块 | 不同变化原因，能隔离职责或依赖 | 仅为缩短文件，拆后仍强耦合 |
| 校验/异常处理 | 不可信边界；能够恢复、补充上下文或转换语义 | 可靠内部契约重复校验；无意义记录后重抛 |
| 条件分支/分发映射 | 稳定同类操作可用数据或处理函数集中变化 | 为降低 if 数量隐藏状态机，或对少量清晰分支引入策略框架 |

复杂度、重复率和文件长度是定位线索，不是重构结论；说明具体修改或排障会因此减少什么成本。

**设计消融**：移除抽象后若不增加重复维护、耦合、修改传播或验证成本，则优先简化；有明确收益的抽象不因增加代码而被拒绝。

## 三、按任务执行

- **新功能**：明确需求、约束、验收标准与规则归属 → 比较最小充分方案 → 实现 → 验证主要路径和必要边界。
- **Bug 修复/调试**：尽可能复现 → 沿输入、异步时序和资源状态定位根因 → 最小充分修复 → 回归验证；不能复现时披露替代证据与缺口，不靠扩大重试或吞错消除现象。
- **架构设计**：明确职责、依赖方向、契约和真实变化点 → 比较直接实现、复用与抽象 → 说明取舍及验证方式；没有编码授权时不改源码。
- **代码优化**：先说明维护、复杂度或性能的具体问题；结构优化验证可读性、修改传播与行为，性能优化建立可重复基线并对比指标，避免无证据微优化。
- **重构**：先固定既有行为与接口契约，覆盖关键行为后逐步修改，减少重复规则与无收益结构。
- **代码审查**：默认只读，优先可验证缺陷和实际维护风险，记录触发条件；不强制制造问题或附带改造。
- **清理/依赖治理**：核实静态和动态引用、运行时及安装发布影响 → 最小删除或升级 → 验证受影响路径；区分锁文件中的传递依赖和业务直接依赖，无关历史问题只报告。

## 四、执行约束与完成标准

1. 先运行 `git status --short`（适用时），理解需求、现有代码、版本和项目约定；重大歧义先确认。Node.js 任务检查 owning code、`package.json`、锁文件、Node/包管理器版本、模块类型及实际启动/构建/测试入口，不只看编辑器配置。
2. 只做**最小且完整**的授权变更，检查必要调用方、配置、测试和部署影响；不顺带重构。
3. 用有依据的变化场景检查：规则是否只需改一处、无关模块是否保持不变、契约是否稳定。
4. 按风险执行测试、Lint、Build 或运行验证；区分**已验证、未验证、验证失败**，设计推演不能代替运行验证。
5. 满足验收标准、必要关联修改和风险匹配的验证后停止；不虚构结果、不擅自扩展范围。

**禁止**：无证据推断调用方或运行行为；未经实际修改或验证就声称“已修复”“已验证”；以“最佳实践”替代具体影响分析；编造测试、日志或运行输出；报告未实际检查的位置或结论。

## 五、审查输出

每项问题列出：**级别、位置、触发条件、证据、影响、最小修复、关键取舍和验证方式**。证据注明是已复现、可推导风险还是待核实观察；严重程度结合实际影响、发生可能性和修复成本，代码风格或指标超限不自动构成缺陷。级别为**阻断**（实际错误/安全/契约风险）、**重要**（有明确影响的设计问题）、**建议**（有具体收益）、**观察**（不确定性及证据缺口）。

结论：**不通过**（确认阻断）；**无法判定**（关键证据缺失，不能排除阻断）；**有条件通过**（无确认阻断，待办明确且风险可控）；**通过**（必要验证完成且无阻断）。不因未执行全部测试自动判为无法判定。

## 七、Node.js 执行要点

涉及相应代码时应用，下列规则的取舍和验证方法见 Reference 八至十一：

1. **保持模块与接口契约**：先确认 ESM/CJS、exports 和实际消费者；避免用转发层或循环依赖模糊 owner。配置和未知工具/网络输入在入口解析，TypeScript 类型不能代替运行时校验；内部按类型使用，只在可变状态或信任边界变化后重检。
2. **让异步工作有归属**：每个 Promise 都由调用者等待、返回或明确的后台 owner 跟踪。区分限制并发、取消等待与终止操作；失败后处理仍运行的同伴任务，不假定 Promise.all 或超时竞争会停止它们。
3. **按执行位置选 API**：同步启动脚本与高并发请求路径分别判断。先测事件循环延迟、CPU、I/O 或内存来源，再决定减少工作、流式处理或使用 Worker；async 包装不会把 CPU 工作移出主线程。
4. **资源从创建管到结束**：文件、流、连接、子进程、监听器和定时器明确 owner、释放顺序及关闭期间的新工作规则。Stream 尊重背压；失败、取消、重试和退出都要收尾，清理失败不能覆盖原始异常。
5. **保留可诊断的错误**：区分业务拒绝、暂时失败、取消和进程/存储故障，不统一吞掉或无限重试。错误码、cause、日志上下文和敏感信息投影由边界 owner 负责。
6. **升级和删除依赖以运行证据为准**：检查直接/传递依赖、动态加载、原生模块、脚本与打包入口；审计通告结合实际版本和路径评估，不凭包名判断，也不自动 force 升级。按变更验证真实 Node 运行路径与安装产物。

**最终标准：规则集中、变化局部、抽象有收益、修改有边界、结论有证据。**
