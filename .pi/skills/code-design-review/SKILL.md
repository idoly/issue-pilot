# Code Design & Review

目标：**正确、复用、职责清晰、变化局部化、整体简洁**。按任务风险应用规则，不增加无收益流程。适用于代码、配置、依赖和构建；仅在授权范围内修改。

## 一、设计原则

1. **正确性优先**：守住业务行为、安全、数据一致性、契约与必要兼容性。
2. **业务知识集中**：同一规则明确归属、统一维护；仅代码相似但语义不同的不强行合并。
3. **变化局部化**：围绕真实变化点组织职责与依赖（依据可来自修改历史、已确认扩展、依赖方向、领域归属或契约稳定性），不为假设需求预建扩展点。
4. **恰当抽象**：抽象须减少重复维护、耦合或修改扩散，收益应超过理解、测试与维护成本。
5. **整体简洁**：优先复用项目惯例、现有实现、标准库与框架能力；不以代码量或文件数衡量设计质量。
6. **证据驱动**：性能先测量，清理先核实引用；不把推测当事实。

## 二、设计决策

先确认**语义、正确性、契约和授权**，再比较直接实现、复用现有能力和新增抽象：

| 决策 | 何时考虑 | 何时避免 |
|---|---|---|
| 合并重复 | 同一业务规则需要同步维护，语义一致 | 仅代码形状相似，失败或业务语义不同，或规则归属不同 |
| 新增接口/策略 | 真实多实现、外部可替换边界或明确的修改扩散 | 单实现、无真实变化需求、增加无收益层级 |
| 拆分类/模块 | 不同变化原因，能隔离职责或依赖 | 仅为缩短文件，拆后仍强耦合 |
| 校验/异常处理 | 不可信边界；能够恢复、补充上下文或转换语义 | 可靠内部契约重复校验；无意义记录后重抛 |

**设计消融**：移除抽象后若不增加重复维护、耦合、修改传播或验证成本，则优先简化；有明确收益的抽象不因增加代码而被拒绝。

## 三、按任务执行

- **新功能**：明确验收标准与规则归属，采用完整且结构合理的最简方案。
- **Bug 修复**：定位根因，尽可能先复现；无法复现时披露替代证据与风险；验证修复及回归。
- **重构**：保持未要求改变的外部行为，减少重复规则与无收益结构。
- **代码审查**：默认只读，只报告有证据的问题。
- **清理**：核实静态、动态引用及运行影响；无关历史问题只报告。
- **性能优化**：先建立基准，后优化并比较结果。

## 四、执行约束与完成标准

1. 先理解需求、现有代码、版本和项目约定；重大歧义先确认。
2. 只做**最小且完整**的授权变更，检查必要调用方、配置、测试和部署影响；不顺带重构。
3. 用有依据的变化场景检查：规则是否只需改一处、无关模块是否保持不变、契约是否稳定。
4. 按风险执行测试、Lint、Build 或运行验证；区分**已验证、未验证、验证失败**，设计推演不能代替运行验证。
5. 满足验收标准、必要关联修改和风险匹配的验证后停止；不虚构结果、不擅自扩展范围。

**禁止**：无证据推断调用方或运行行为；未经实际修改或验证就声称“已修复”“已验证”；以“最佳实践”替代具体影响分析；编造测试、日志或运行输出；报告未实际检查的位置或结论。

## 五、审查输出

每项问题列出：**级别、位置、证据、影响、最小修复、验证方式**。级别为**阻断**（实际错误/安全/契约风险）、**重要**（有明确影响的设计问题）、**建议**（有具体收益）、**观察**（不确定性及证据缺口）。

结论：**不通过**（确认阻断）；**无法判定**（关键证据缺失，不能排除阻断）；**有条件通过**（无确认阻断，待办明确且风险可控）；**通过**（必要验证完成且无阻断）。不因未执行全部测试自动判为无法判定。

**最终标准：规则集中、变化局部、抽象有收益、修改有边界、结论有证据。**
