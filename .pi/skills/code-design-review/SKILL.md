# Code Design & Review

遵循**正确、简单、复用、内聚、最小、可维护**的原则。根据任务类型和风险选择执行策略，不机械套用所有规则。

适用于项目代码、配置、依赖及构建治理。生成代码与第三方代码仅在授权范围内修改。

## 一、设计原则

1. **正确性优先**：保障业务正确性、安全性、数据一致性、必要兼容性及可诊断性。
2. **简单与复用**：优先使用现有框架、标准库、依赖及官方扩展能力，避免重复造轮子和无意义封装。
3. **合理抽象**：仅在能够降低重复维护成本、隔离真实变化点、明确职责边界或控制修改扩散时引入抽象；综合权衡收益与复杂度，不以重复次数作为硬性门槛。
4. **高内聚、低耦合**：避免业务写死、重复规则、过度拆分、万能模块及无收益调用层级；遵循项目合理约定。
5. **证据驱动**：不为假设需求、性能瓶颈或所谓最佳实践增加复杂度。
6. **精简治理**：识别无效代码、配置、文件及冗余依赖；核实用途后，在授权范围内安全清理。

## 二、按任务类型执行

- **新功能**：明确需求与验收标准，选择最简单且完整的实现，合理支持真实变化。
- **Bug 修复**：定位并尽可能复现根因，避免用额外兜底掩盖问题，最小范围修复并验证回归。
- **重构与简化**：保持既有外部行为，减少重复、过度拆分和无收益抽象。
- **代码审查**：基于证据报告实际问题，默认只读，不擅自修改。
- **冗余清理**：核实静态与动态引用、构建及运行影响，在授权范围内安全删除。
- **性能优化**：先测量瓶颈，再针对性优化，通过前后数据验证收益。

## 三、执行约束

1. **先理解再行动**：核实需求、代码、依赖版本及现有能力；明确关键假设，重大歧义先询问，低风险且可回退的假设可说明后继续。
2. **最小且完整的变更**：仅修改必要范围，同步处理必要关联修改，并清理本次变更产生的冗余；不擅自处理无关历史问题。
3. **影响范围发现**：根据变更类型与风险，检查相关调用方、配置、依赖、动态引用、测试及构建部署影响，不进行无关检查。
4. **消融检查（必要性检查）**：审视新增代码、抽象、接口、配置、依赖和调用层级；若移除或简化后仍满足需求及必要质量约束，则不保留。
5. **严格任务边界**：审查默认只读；修改仅限授权范围及必要关联变更，范围外问题只报告。
6. **目标驱动与 DoD**：明确可验证的完成标准；满足需求、完成必要关联修改、清理本次冗余并完成风险匹配的验证后停止，不扩大范围。
7. **验证闭环**：按风险执行测试、Lint、Build 或运行检查；区分已验证、未验证与验证失败。无法验证时说明原因和风险，不虚报结果。

## 四、审查输出

按严重程度报告问题：

- **阻断**：明确且不可接受的正确性、安全性、数据一致性或兼容性风险。
- **重要**：明显增加维护成本或违反关键约定。
- **建议**：具有明确收益的改进。
- **观察**：暂不影响当前需求的潜在问题。

每项问题说明：**位置、证据、影响、最小改进方案、验证方式**。

整体结论：

- **通过**：未发现阻断问题，必要验证已完成。
- **有条件通过**：无已确认阻断问题，但存在明确待完成事项。
- **不通过**：存在必须解决的阻断问题。
- **无法判定**：证据或验证不足，无法可靠判断。

结论应基于当前已有证据。因关键验证缺失而无法排除阻断风险时，使用“无法判定”并说明缺少的证据或待验证项，不用“有条件通过”替代。

没有明确问题时保持现状，不强行重构。

## 五、详细规则

涉及原则冲突、复杂影响分析、验证矩阵、例外处理、依赖治理或清理授权时，按需读取 `references/code-review.md`。

**最终要求：没有必要，不增加代码；没有证据，不增加复杂度；能局部解决，不扩大范围；不为设计而设计，不为简化而写死，不为清理而误删。**
