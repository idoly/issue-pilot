# Code Design & Review — Reference

按 `SKILL.md` 第六节的信号读取对应节，不必通读；冲突时以 `SKILL.md` 为准。

## 一、设计取舍裁决

优先级：正确性、安全、数据一致性及明确契约 > 必要兼容与完整性 > 业务规则统一维护和变化隔离 > 整体简洁与认知成本。真实需求决定权衡，不因设计模式增加结构。

| 维度 | 关键问题 |
|---|---|
| 规则归属 | 同一业务知识是否只需维护一处？ |
| 复用语义 | 复用的是相同语义还是仅代码相似？ |
| 变化传播 | 一项有依据的变化会触及哪些模块？ |
| 内聚 | 因相同原因变化的数据和行为是否在一起？ |
| 耦合 | 调用方是否依赖不必要的实现细节？ |
| 抽象收益 | 新接口或层级是否降低整体成本？ |
| 可验证性 | 规则和边界是否容易测试与定位？ |
| 约定一致性 | 是否复用项目已有结构与官方机制？ |

## 二、常见设计决策

| 决策 | 采用条件 | 不采用时 |
|---|---|---|
| 提取方法 | 逻辑有独立意图、可复用规则或明显提升可读性 | 无语义价值的纯转发可内联 |
| 提取公共逻辑 | 相同业务语义且确实降低重复维护 | 语义不同则独立维护 |
| 引入接口 | 真实多实现、可替换外部依赖或清晰跨模块契约 | 单实现且无替换需求时按项目惯例直接使用 |
| 引入策略/多态 | 多种真实行为、分支散落且有变化成本 | 少量稳定分支使用条件表达式 |
| 拆分模块 | 不同变化原因或需要隔离依赖 | 仅为缩短文件不拆 |
| 捕获异常 | 能恢复、补充必要上下文或转换语义 | 不做无意义记录后重抛 |
| 增加校验 | 不可信输入、外部边界或契约保障不足 | 不重复证明可靠契约 |
| 添加注释 | 解释原因、非显然约束或取舍 | 不复述代码 |
| 新增依赖 | 现有能力不足且整体成本可接受 | 优先已有能力与官方机制 |

## 三、消融与变更检验

对新增代码、接口、层级、配置和依赖，比较直接实现、复用和新增抽象的成本：去掉它后，是否增加业务规则重复、修改传播、耦合、测试难度或明确的兼容风险？若无实际收益，优先删除、合并或内联。

**变更检验**：选一个有依据的变化场景，推演：

1. 同一规则是否只需修改一处？
2. 无关模块是否保持不变？
3. 现有契约是否得到保持？

这是设计推演，不等同于运行测试；不为假设需求编写实现。

## 四、影响范围发现

按风险选择，不要求全部执行：

- **静态引用**：符号、字符串、路由、事件、配置键。
- **依赖关系**：调用方、模块、包、构建依赖。
- **动态机制**：反射、DI、插件加载、序列化注册、模板字符串。
- **契约与测试**：接口调用、兼容性、既有测试。
- **运行与部署**：数据库迁移、配置、构建产物、部署流程、回滚方案。

无法排除关键风险时说明证据缺口，不擅自扩大修改。

## 五、风险匹配的验证矩阵

以下是优先证据，不是所有任务都必须执行的固定清单。无法取得时说明替代证据、限制与风险。

| 任务 | 验证重点 | 优先证据 |
|---|---|---|
| 新功能 | 验收标准、主要路径、边界条件 | 通过的测试或可复现运行记录 |
| Bug 修复 | 根因、修复有效性、回归 | 可行时修复前失败、修复后通过的测试；否则提供根因及替代验证 |
| 重构 | 行为与契约保持、结构收益 | 变更前后同一组相关测试通过 |
| 接口变更 | 调用方、错误语义、兼容性 | 调用方检查、契约或集成测试 |
| 依赖变更 | 解析、构建、运行时加载 | 构建和相关运行路径检查 |
| 配置变更 | 启动、环境差异、恢复方式 | 受影响环境的启动或配置验证 |
| 数据迁移 | 一致性、顺序、恢复 | 安全环境演练、恢复方案验证 |
| 清理 | 静态/动态引用、构建、部署影响 | 引用检索及相关构建/运行检查 |
| 性能优化 | 基准、前后对比、功能回归 | 可复现基准数据与相关回归测试 |

**报告口径**：已验证列执行项与结果；未验证列原因与风险；验证失败列现象及影响。静态检查、构建成功、运行验证不能互相冒充。

## 六、测试设计要点

1. **锁定规则归属**：优先在业务规则归属点直接测试核心行为；接口、集成及端到端测试可从不同层次验证同一规则实际生效，避免没有额外价值的重复断言。
2. **保护重构**：确认现有测试覆盖被修改的可观察行为；不足时优先补充特征测试，再重构。
3. **约束边界**：外部输入、外部依赖、序列化及契约变化按风险增加边界测试；内部可靠契约不必机械重复测试。

审查关注：测试是否断言行为而非实现细节；关键规则是否只覆盖 happy path；测试替身是否掩盖真实依赖语义。

## 七、例外与真实任务回放

高风险例外按需记录事项、原因、影响、验证、后续、授权人；低风险任务不强制模板。

**实证验证 Skill**：从已有代码库选择 3–5 个真实历史任务，优先包含过度抽象、漏改 Bug、接口变更、清理、性能问题。对每个任务：

1. 固定任务描述、当时的代码基线和允许修改范围。
2. 记录历史真实问题与可验证的预期结果。
3. 在相同条件下回放，观察 Agent 是否识别原问题、完成必要修改与验证。
4. 记录新增的无效建议、无收益抽象、漏改与越界修改。
5. 只针对反复出现、证据明确的失败调整规则或替换为真实代码案例。

不要把通用示意案例标成真实项目证据；没有回放结果时，不宣称 Skill 已验证有效。无需为回放新建固定模板或额外目录。

## 八、Node.js 模块与契约

先沿实际启动入口和调用方定位 owner，再决定模块调整。修改某条规则时，比较需要改动的模块、导入方向和测试替身：若业务层只为转发某个 SDK 类型而逐层依赖它，考虑在真实边界隔离协议；若封装没有隔离变化或错误含义，则保留直接调用。循环依赖要核对初始化顺序与共享状态，不能只把 import 移进函数掩盖问题。

| 场景 | 如何选择与修改 | 验证重点 |
|---|---|---|
| ESM/CJS 或包入口变化 | 核对 type、扩展名、exports、import/require 条件和真实消费者；考虑默认导出、路径解析、缓存身份及双入口是否创建两份单例；不为风格统一强行转换 | 用受支持 Node 和实际消费方式加载；库/CLI 检查打包安装后的入口，不只运行源码 |
| API、配置和公共错误变化 | 明确参数、返回值、缺省、错误码、兼容范围及副作用 owner；把 unknown 解析放在入口；配置先校验再发布，长任务明确使用快照还是热更新 | 合法、缺失、错误输入，旧调用方及更新期间的行为；不把 TypeScript 通过等同于运行时校验 |
| 分支与抽象增多 | 区分稳定业务状态、输入校验和可替换操作；同类分发可用表或函数，复杂状态保持显式转换；圈复杂度和重复率用于找热点，重构收益要落到理解和变更成本 | 契约与失败路径保持；新增一种真实操作是否局部；不以减少 if 或文件长度为验收目标 |
| 隐式副作用和重复状态 | 查模块加载、顶层 await、全局缓存和可变配置的时机；资源需要 owner 时再提供初始化/关闭入口，避免一导入就启动服务 | 并发初始化、初始化失败、测试隔离及关闭；不为纯函数增加生命周期接口 |

## 九、Node.js 异步与生命周期

修改异步代码前，用时序说明“谁启动、谁等待、谁取消、谁收尾、谁能发布结果”。类型相同但资源 owner、事务或取消语义不同，不强行合并。

- **Promise 与错误传播**：调用者应 await/return，后台工作则由明确 owner 跟踪完成和拒绝。检查异步事件回调的拒绝由谁接收；普通 EventEmitter 不自动等待 async 监听器。catch 只在能恢复、转换边界含义或补充上下文处使用；需要追踪根因时保留 cause，勿统一返回空值掩盖故障。
- **并发与竞态**：对读→等待→写过程标出共享可变状态、可重复副作用及提交点。单线程不排除 await 间的竞态；按实际资源键串行或使用版本/事务检查，不默认全局加锁。Promise.all 的快速失败不会取消已启动任务；有外部副作用时定义失败后的同伴收尾，再决定 allSettled、取消或有界工作队列。
- **过期与取消**：区分取消调用者等待和真正停止操作。需要停止 I/O、子进程或 Worker 时把信号传到执行 owner，检查结束后仍可能到来的结果。版本号、请求身份或提交时校验用于阻止旧结果覆盖新状态；重复做入口校验无法解决时序问题。
- **超时与重试**：Promise.race 超时不等于终止底层操作。按业务期限定义连接/单次请求/整体预算，并清理计时器。重试仅针对可恢复错误，考虑次数、退避、取消和幂等键；结果未知的写入先核对，不凭超时重放。避免多层重试相乘或每次重试重置整体期限。
- **Stream 与大数据**：先确认最大数据量和完整性语义。大输入按块处理或使用 pipeline/异步迭代；写入返回 false 时处理背压，不把流收集成无界字符串再称作流式。预算同时考虑上游读取、解析/解压、下游缓冲；截断要显式表达，不能冒充完整成功。验证中途错误、取消、慢消费者及句柄关闭。
- **资源与清理**：连接、文件句柄、监听器、定时器、子进程在获得后明确释放责任，覆盖初始化部分失败和重复关闭。仅释放本 owner 的资源，等待必要的后台任务；关闭顺序依据真实依赖。清理与业务同时失败时保留主异常并附带清理错误，可使用 cause/AggregateError；不能让 finally 中的新异常覆盖根因，也不静默吞掉清理失败。
- **进程退出**：区分正常信号关闭与未捕获故障。需要优雅关闭的服务先停止接收工作，再按预算等待或取消、刷新输出、释放资源；不要靠立即 process.exit 或 unref 代替收尾。故障后的状态若无法证明一致，记录诊断并退出，不靠全局异常处理器盲目继续。一次性 CLI 不必引入服务级关闭框架。

## 十、Node.js 调试、性能与行为验证

调试先缩小到触发输入、调用路径、运行版本和时序，获取最小复现。必要时使用堆栈、cause、断点、请求/任务 ID、资源计数或事件记录，避免仅凭某条日志推断整体成功。诊断不得输出密钥或未经脱敏的业务载荷。

| 观察到的现象 | 优先取证 | 有依据后的改动方向 |
|---|---|---|
| 请求慢、吞吐下降 | 分开测端到端、排队、外部 I/O、CPU 与事件循环延迟；需要时用 perf_hooks、CPU profile 或火焰图 | 减少重复工作、查询或序列化；限制并发；仅对明确 CPU 热点评估 Worker，计算传输/启动成本 |
| 大输入卡住或内存持续增长 | 对比输入规模、RSS/heap、缓冲和队列长度；必要时比较堆快照及保留引用，区分缓存、原生内存和真实泄漏 | 有界队列、背压、释放监听器/闭包引用；缓存须明确失效和容量，不通过加堆大小代替定位 |
| 取消无效、重复执行、退出挂住 | 重建请求与资源生命周期，观察取消后操作是否仍运行、是否有存活句柄/子进程；不只看接口已拒绝 | 修复 owner、信号传递、幂等提交或关闭顺序；不要用缩短超时和强制退出掩盖问题 |

同步 API 在 CLI 初始化、构建脚本或小型低频工作中可能合理；请求热路径中的同步 I/O、巨大 JSON 解析、正则或压缩计算则需结合规模和指标判断。async/await 不会把 CPU 工作移出 Event Loop；大量微任务同样可能延迟 I/O。不要把“同步”一律判成缺陷。

性能对比固定 Node/依赖、数据规模、预热、并发与环境，记录延迟分布、吞吐或内存等目标指标及测量波动，同时验证功能一致。维护性优化可用重复规则、修改传播和控制流证据说明收益，不强迫做无关性能基准。

测试按风险选择：纯规则用单元测试；协议、模块装载、文件与数据库边界用集成测试；并发和取消用可控屏障/信号明确时序，避免依赖任意 sleep。故障注入应断言最终状态、外部副作用和资源释放，而不只断言“抛了异常”。重构先补关键特征测试，修改后用同一行为验证，必要时覆盖失败、重试、重复调用和关闭。

静态分析、历史记录、运行测试和推断分别报告。覆盖率可提示遗漏路径，不能证明测试有效或替代并发/失败场景。没有真实负载、平台或凭证时说明缺口，不把 mock 通过声称为线上验证成功。

## 十一、Node.js 工程、依赖与执行边界

依赖治理先建立 package.json、锁文件和真实使用路径之间的关系；删除和升级是不同任务，不顺手把清理扩大为全量更新。

1. **识别依赖角色**：检查 import/require、动态 import、Worker 入口、插件、bin、脚本、构建资源与生产部署。直接使用的包应直接声明；构建期和运行期按产物实际需要划分，包出现在锁文件不等于业务冗余。不能仅凭文本搜索未命中删除动态资源。
2. **评估变更**：确认支持的 Node/包管理器、安装平台、API/行为变化、原生 ABI、可选依赖及安装脚本。选择满足当前问题的最小版本范围；重大升级、换框架或锁文件迁移需已有授权。审计结合受影响版本、实际调用和部署暴露面说明风险，未验证可达性就标明；不自动 audit fix --force，不以改版本号代替验证。
3. **验证安装与发布**：使用项目既定的锁文件和安装工具，核对清洁安装、生产依赖裁剪、构建和真实入口。涉及 exports、bin、TS 转译、条件导出或资源路径时，测试安装后的包/容器，不只测仓库源码。Node 新 API、原生 TS 支持、加载器和构建目标以实际支持矩阵为准，不擅改最低版本掩盖兼容问题。
4. **配置、日志与诊断**：默认值与环境解析集中在配置 owner，明确缺失值、快照/热更新和凭证来源。按需要记录操作、稳定错误码、耗时和关联 ID；保留内部错误原因，对外投影脱敏。不要整份打印 env/config、请求认证头或带密钥 URL。日志量和大对象序列化也计入运行成本。
5. **命令与路径**：不可信文本进入 shell、argv、文件或 URL 前在 owner 校验。执行程序优先参数数组；参数数组仍需考虑选项注入、解释器语义和环境继承。路径处理明确是否跟随链接、是否允许越界及覆盖；涉及攻击面或竞争时才增加 realpath/文件描述符等检查，不把 cwd 或 resolve 当作沙箱。
6. **网络和输入**：检查实际可控的目标、重定向、认证头传播及响应预算。根据暴露面处理 SSRF、跨目标凭证泄露、超大/压缩响应和解析成本；协议类型正确不等于业务目标已授权。按契约处理 Buffer/文本编码、数值精度和 JSON 不可表示的值，不用类型断言替代未知输入解析。

## 附：通用设计正反例（非项目实证）

| 场景 | 推荐 | 避免 |
|---|---|---|
| 多处重复判断订单是否可取消 | 将同一规则集中在归属模块 | 在多个入口复制条件 |
| 用户时区与结算时区的格式化 | 显式表达不同语义 | 无参数函数错误合并 |
| 仅一个支付实现且无替换需求 | 按项目惯例直接实现 | 预建完整策略层次 |
| 已有多个支付网关 | 在真实边界隔离差异 | 在各调用方散落分支 |
| HTTP 异常转换 | 在边界映射错误语义 | 多层重复记录并重抛 |

这些是说明性案例，不代表已通过真实项目验证。
