# 配置设计的已确认边界

前一版三列表方案和独立草图已撤回，尚未实施页面管理与数据库权威源切换。

## 保留的用户凭证部分

用户认可现有凭证分组，保留模型 API Key、Git SSH、DMS 和 SLS。角色、管理员权限、凭证归属和当前身份切换规则保持原样，不新增用户与仓库／服务的绑定。

用户不维护钉钉凭证。钉钉统一使用已配置的全局 MCP 连接；个人 API Key／连接地址覆盖逻辑、个人状态字段、页面条目及导出／补齐能力已删除。用户自己的钉钉表格来源和字段映射属于业务偏好，继续保留。

## 服务和仓库的后续设计约束

- 以新增服务、增加代码仓库和调整环境分支这些常见操作为起点，避免要求操作者先理解配置文件和内部别名。
- 仓库只登记一次，可被多个服务复用；是否保留独立仓库入口尚未定版，不能只把原有大表单搬到新标签页。
- 人员变化只管理账号、状态、角色和个人凭证；不要求同步改服务与仓库。
- 文件与页面不能同时作为权威来源。若采用页面维护，必须一起完成持久化和启动逻辑，避免重启覆盖页面保存内容。
- 延续现有页面的紧凑布局，下一版交互需要针对具体操作说明，不沿用已撤回的独立草图。

## 本轮已经实现的相关代码优化

仓库显示名修改不再预约或关闭运行中的工单。仓库地址修改只预约绑定服务的入口工单和跨服务包含工单，不再查询和阻塞全部工单；历史仓库记录仍保持原样。相关回归已覆盖原失败触发及修复结果。

这些局部优化不改变当前文件配置模式，也不代表配置页面已恢复增改删。
